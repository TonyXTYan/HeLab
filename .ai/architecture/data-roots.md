# Data roots

Reference detail for agents working in this area. It moved here verbatim from `AGENTS.md` on
2026-10-28, when AGENTS.md was cut to rules and a map ([index](README.md)). AGENTS.md keeps the
rules every task must follow; this file keeps the mechanics, names and behaviour. Keep it true:
on Ground, update it in the same commit as the code; on a floor, propose the change in your handoff. Settled decisions and Tony's wording live in
`.ai/memory/results/`; feature plans in `roadmaps/`.

**Data roots:** Disk caching needs a **data root**: a folder holding a hidden `.helab-root` JSON marker (`helab/utils/data_roots.py`: `{"helab": "root", "version": 1, "uuid", "label", "created_at"}`; unknown fields are ignored, an invalid marker is no root). A folder's cache key is `root://<uuid>/<relative>` from the nearest marker at or above it; nested markers are allowed. **Without one the folder uses RAM only**: nothing is read from or written to the store for it, with no fallback to path keys. Folder details then says "RAM only · no .helab-root found here or above", but only when a helper reported it (`FolderCache.no_root`), never because a root is unknown. The store's `roots` table maps **location** keys to UUIDs (`helab/utils/cache_paths.py`): `smb://server/share/relative` for shares (server and share lowercased, SMB account omitted, `/Volumes` suffixes ignored; Windows mapped drives and UNC paths alike) and `vol://<OS volume ID>/relative` for local volumes, so two same-named USB disks never share a location. Matching is case-insensitive on SMB and Windows volumes, but keys keep the source path's spelling.
- **Discovery:** with the disk cache on, a listing lstats its own folder's `.helab-root` before its scandir, then reads and reconciles the marker (`_discover_root`: `root_found`, `root_changed`, `root_duplicate`). A marker found below an outer root re-keys that subtree's rows in one transaction (newer wins). A replaced marker starts fresh. An unreadable marker keeps the row; an invalid one forgets it and, like a removed one, sends `root_changed` (reason `marker invalid`), so tabs drop the root. If the folder's key changed, the entries are sent again with `replace`. A view's `root_key` is quoted exactly as the store's keys (`dataset_view.root_key`, C-15); arrangement and reopen records saved before with unquoted keys (paths with spaces) don't match. Results (list and scan status, cached and load `loaded`) carry `data_root`, so tabs know a folder's root without listing the root folder.
- **Local lane:** it uses only the `roots` table and the `root_volumes` hints that source helpers record. Source helpers also record each mount's share or volume (`mount_hints`: mount path → `smb://server/share` or `vol://<id>`, never the system volume's) so that offline an unmounted path still has a key (`stores._offline_mounts`): a hint is used only offline and only when nothing is mounted at its path or above it now apart from transparent mounts (the system volume and pseudo filesystems, `TRANSPARENT_FILESYSTEMS`); any other current mount (disk, share, NFS, FUSE, autofs, unknown) wins (`_transparent_mount`). Cached reads, subtree saves and scan-history writes trust only the hints this session's verification checked (`verified_volumes`, from the local-lane `volumes_verify` at startup and after a mount change), plus the system volume's. On any other volume they wait (`VolumeUnverified`) and the cached read is retried on `volumesVerified`. `roots_verify` (background, after other background work queued later: nothing waits for it) re-reads known markers. A listing asks for both again only when it reports a mount table they weren't asked for.
- **Placing one:** right-click › **Place .helab-root here…**, or **File › Place .helab-root…** for the current tab's selected folder (at first its top folder, which isn't a tree row, e.g. a drive's top; `HelabMainWindow.update_place_root_action` on `aboutToShow`), runs `root_create` in the foreground. It writes the marker with exclusive create (hidden: dot name, Windows hidden attribute, macOS `UF_HIDDEN`). It first checks for a folder that isn't the top of its drive or share, is inside another root, is a home folder, the startup disk's top (`/`, never offered) or `/Volumes` (`DataRootDialogs.placement_checks`); with warnings, Cancel is the default button. Markers go as high as every machine sees the data: Windows `C:\` is a drive top like any other (a note says it may need admin rights). An existing marker is adopted; an invalid one is never overwritten. Without write permission, `ManualMarkerDialog` hands out the exact JSON (Copy, or Save to folder… writes `.helab-root` under its exact name through the `marker_save` helper, in the foreground like `root_create`, and says how to show hidden files). RAM-only folders grey out Don't cache / Don't auto-load and Clear loaded data cache. Root folders show the ANCHOR badge beside their status icon.
- **Duplicates:** the same UUID at a new location is pending, and RAM only, until the user answers in `RootDuplicatesWindow`. It opens once per location per session: Later asks again at the next sighting, Remind me next session not until the next session, and the status bar shows "⚓ N to confirm". **Same folder** runs `cache_admin root_same`. **It's a copy…** runs `root_reassign` in the foreground: the other side gets a new marker, and the side keeping the original UUID keeps the data. Until then the tree warns on that folder and its shown descendants (ROOT_PENDING, an amber alert triangle beside the status icon, from `FolderCache.pending_root`; rows refresh on `rootDuplicatesChanged`), the row tooltip says "Data root “label” also seen at <other>: same folder or a copy? RAM only until answered.", the summary's cache line says "RAM only · this .helab-root is also at another location" with a Review… button, and Settings → Data roots has Review… on pending rows; all open the window at that location (`HelabMainWindow.review_root`, modal when Settings is open). Same folder, It's a copy… and a forgotten or removed location (`root_changed` with its location) settle it. A pending location whose other locations have all been forgotten is confirmed by its next listing.
- **Settings → Data roots** (`helab/views/DataRootsTab.py`) lists the locations and forgets one (`forget_root`). A forgotten location is found again while its marker is there. Clear all never touches `roots`. A row's menu also has Show in Finder / File Explorer / File Manager (reveals the hidden marker; a detached launch, no source I/O in the GUI) and Copy path; **Delete .helab-root…** (also a footer button; Cancel default) runs `root_remove` in the foreground: it deletes the marker only if it is still a regular file holding the row's UUID, then forgets that location and those below it with the UUID (cached data stays under the UUID), or without permission names the file (`root_remove_refused`). Open tabs list that folder, and their top and selected folders inside it, again (`rootDecided`). Not-mounted rows can't be shown or deleted. **Clear cached data…** (button and menu item, any row, mounted or not; the list's Cached column and the confirmation give the size from the inventory's `cached`) runs `cache_admin clear_root`: every record, dataset and pending save keyed below `root://<uuid>` goes in one transaction, with that root's epoch bumped (`folder_epochs` row `root-clear://<uuid>`, which every save guard below the root checks) so a save already running can't bring data back; `roots`, folder flags and the marker stay, dataset files are retired, and `removed` resets RAM flags. The user's marker writes (`root_create`, `root_reassign`, `root_remove`, `marker_save`) run in the foreground whoever asked (`MARKER_OPERATIONS`).
- **Unsupported mounts:** NFS, AFP and WebDAV mounts stay unsupported for disk caching ("Disk cache off" line per mount per session; Windows WebDAV UNC paths included). Two SMB accounts on one share use the same rows.
- **Fresh store:** the store is `store-v3`, which started empty; `store-v2` is left on disk unused, and can be moved to the Trash by hand.
- **Network plan:** the root UUID is the planned cross-machine logical root ID; location keys stay local (`roadmaps/network-runners-and-web.md`). Design: `roadmaps/data-roots.md`.

Session-only `FolderCache` and open tabs still use source paths. If shares remount while HeLab stays open and macOS reorders `/Volumes` suffixes, toolbar Refresh relists the shown branches and, when saved records can be read, replaces their RAM status, failure history and derived status with the newly mounted share's saved results. It leaves RAM datasets available but unchecked, so the next selection checks them. A background details pass re-observes folder dates for freshness hints. Restart HeLab to refresh other paths and other tabs' loaded data. A load checks TXY files and reports mismatched folders when files have disappeared, but a stale derived subfolder status can be saved under the newly mounted share and show an amber clock until its children are checked. Live tab rebinding is future roadmap work (offline browsing of roots is built: Work Offline, [io-and-browsing](io-and-browsing.md); its follow-ups are in `roadmaps/cache-only-browsing.md`).
