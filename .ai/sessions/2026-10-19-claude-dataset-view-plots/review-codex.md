# Codex review — Dataset view plots

Branch `agent/dataset-view-plots`, base `376c7dd`, reviewed at `e7f4e61`.

## Verdict

**Changes requested.** The numerical crop is not the shortest range advertised to users, and the view does not enforce its claimed immutable snapshot. Cancellation also needs a test and a policy for long computations. All changed paths are within the brief's ownership. I found no new experiment-folder I/O in the GUI; building the view reads the already displayed `Dataset` and cached root hint. Script loading does hash local Python files in the GUI, which is separate from experiment source I/O.

## Findings

1. **Major — `helab/analysis/dataset_view.py:114` and `:177`: a script can modify the browser's shot through the view.** `read_only` returns an already read-only array unchanged. The normal `FolderCache` path calls `array.setflags(write=False)` on the received array (`folder_cache.py:2006`); an analysis can sometimes call `context.view.shots[shot].setflags(write=True)` and write into the very array held by `FolderExplorer.displayed_dataset`. I reproduced this with an owning `(1, 3)` NumPy array, and separately with the helper's `np.save`/`np.load` path (`io_service.py:650`): after toggling the flag, writing 99 through the view changed the source array to 99. A read-only view backed by immutable bytes *does* refuse the toggle, so the precise backing storage matters. For an initially writable array, `read_only` makes a read-only view but the original writable array can change during a run; the existing test explicitly permits this. This violates the immutable input and selection-independent result contract. **Fix:** decide whether scripts are trusted. For a strong immutable boundary, give analyses private arrays (copy or immutable backing storage) and account for their RAM cost. If zero-copy sharing is required, make this a documented cooperative read-only convention rather than claiming that `DatasetView` prevents mutation; add a test showing the chosen behavior on an actual loaded shot and when the original array is changed mid-run. Apply the same rule to arrays passed to `with_shots()` (`:104–111`).

2. **Major — `helab/analysis/stats.py:103–124`: greedy peeling can retain a grossly wider range than necessary.** It chooses the next face by its *immediate* gain. For six events with T values `[0, 1, 2, 3, 100, 101]` and constant X/Y, `crop_box(events, 4/6)` returns T `[1, 100]` (four events), whereas `[0, 3]` also holds four and is much narrower. The implementation is a heuristic and does not do what the scatter and histogram parameter help claims (`helab/scripts/standard/scatter_3d.py:20`, `helab/scripts/standard/basic_plots.py:20`). A clustered or flat tail can similarly consume the crop budget without exposing the gap to the main cloud. **Fix:** for one-axis histograms, compute the exact shortest sorted sliding window. For 3D, either implement and test a clearly specified joint-box objective or describe peeling honestly as a heuristic and offer a way to select the cloud ROI. Add this adversarial case to `tests/test_analysis.py`.

3. **Major — `helab/analysis/stats.py:88–98` and `helab/scripts/standard/scatter_3d.py:74–79`: 99% of *raw* events is a poor default for a cloud on uniform background.** In the supplied `txy_histograms_dock.png`, the narrow peak is around 3.84–3.86 s, but the 99% T range reaches roughly 4.16 s. The handoff says 2% of events form the late tail: retaining 99% of all events necessarily keeps at least half of that tail even with an optimal box. Thus this behavior follows the chosen statistic, not just a peeling implementation error. It leaves the peak visually compressed and makes a 3D plot's axis range similarly broad. **Fix:** choose a cloud-oriented default after validating on lab data, for example estimate a flat background from sidebands, identify the density peak, then retain 99% of estimated *signal* around that peak; expose the bounds or allow a manual ROI. If the decided 99%-of-all-events rule must remain, label it plainly and add a lower keep preset suitable for this example. Do not describe 99% raw retention as isolating the atom cloud.

4. **Minor — `helab/analysis/runner.py:55–60`, `:85–87`; `helab/models/ScriptTreeSelector.py:217–228`: closing a dock does not promptly stop the bundled computations.** Close sets a cancellation event and disconnects the slot, but the scatter and histogram `compute` methods do not check it, and `crop_box` has no cancellation hook. The running job continues on the sole FIFO worker until it finishes, retaining its input arrays and delaying subsequent runs. The final result is discarded for a cancelled job, and `AnalysisInstance._finished` guards closed docks, so I did not find a direct post-close widget write. **Fix:** check cancellation between major phases and during long crop work, or explicitly bound computation and document that cancellation only suppresses delivery. Add a GUI test that closes a dock *while* a blocked computation is active, releases it, and verifies no render or post-close delivery; the existing close test closes only after a completed rerun (`tests/test_analysis_gui.py:177–204`).

5. **Minor — `helab/analysis/runner.py:66–74`: `stop()` can leave two workers using one queue.** It clears `_thread` before joining for up to five seconds. If a script ignores cancellation longer than that, a later `submit()` creates another worker while the old one remains active. The sentinel can then be consumed by either thread, so FIFO and single-worker execution are no longer assured. **Fix:** keep the worker registered until it actually exits; reject submissions during shutdown or use a distinct restart lifecycle, and test a blocked computation across the join timeout.

6. **Nit — `helab/scripts/base.py:100`:** `git diff --check 376c7dd..HEAD` reports a new blank line at EOF. Remove it before integration.
