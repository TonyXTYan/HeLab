    Script contract¶

    helab.scripts.base ¶

    The script contract: the base classes every HeLab analysis script derives from.

    A script is a Python file whose class derives from DatasetAnalysis (an analysis of one loaded dataset) and names itself with ScriptMetadata. HeLab lists its actions in the Scripts panel; running one calls compute on the analysis worker thread with an AnalysisContext (the read-only DatasetView and the effective parameters), then render on the GUI thread to draw the result in a plot dock. Every other method has a default, so a script overrides only what it needs.

    This module imports no Qt at run time (tests/test_headless_imports.py): a script's compute and its tests run without a display.

    PLOT_MINIMUM_SIZE module-attribute ¶

    PLOT_MINIMUM_SIZE = (200, 200)

    A plot's least size in its dock, (width, height) in Qt's logical pixels; the default of DatasetAnalysis.minimum_size.

    ScriptMetadata(
    name: str,
    description: str,
    group: str,
    file_path: str,
    script_id: str = "",
    analysis_id: str = "",
    version: str = "",
    file_hash: str = "",
)

    Metadata for a HeLab analysis script.

    Attributes:

    • name (str) –

      What the Scripts panel and the plot dock call the script.

    • description (str) –

      One sentence on what it shows, for the Scripts panel's tooltip.

    • group (str) –

      The Scripts panel section it is listed under.

    • file_path (str) –

      The script's file.

    • script_id (str) –

      The ID HeLab gives the loaded script, <file path>::<class name> ("" until it is loaded).

    • analysis_id (str) –

      A stable ID that never changes, across renames and versions; results record it.

    • version (str) –

      A version the author bumps whenever the output changes; results record it beside the ID.

    • file_hash (str) –

      SHA-256 of the script file as loaded (set by HeLab; "" if unreadable). When the folder has helper modules the scripts import, it is instead a SHA-256 of the file's hash and every helper's path and hash, so a change to a helper counts too; it then differs from the file's own SHA-256.

    DatasetAnalysis ¶

    Bases: HelabAnalysisScript

    An analysis of one loaded dataset.

    The Scripts panel runs an action on the current tab's dataset view: compute gets an AnalysisContext (the immutable view and the effective parameters, never the tab) and runs in the analysis worker thread, so it must not touch Qt widgets. render then builds the plot dock's content from the result on the GUI thread. Arrays in the view are shared and read-only: copy one before changing it.

    A plot of the folder Live watches follows it: HeLab reruns it on each newer revision of the view, as the script's live_policy allows. A script never reads files or watches folders itself, and a view may have no shots yet (Live started before the first one): its plot then shows that it is empty, not an error.

    Metadata must give analysis_id and version. Parameter values are plain JSON values (numbers, booleans, strings).

    An analysis that uses physical constants adds constant_layers.constants_specs(keys) to its parameters: the plot's settings then show each constant's value and source, and can set it for that plot. Each run gets the lab and folder layers in context.constants and, resolved with the plot's own values when it was submitted, context.resolved_constants, which its result records; compute reads them there, never from the table's defaults. An analysis with its own override parameters declares constant_keys and run_constants instead.

    parameters ¶

    parameters(action_name: str) -> List[ParameterSpec]

    The action's parameters (defaults, limits, units).

    The plot's settings show them as a tree, and compute gets their values, checked and clamped (ParameterSpec.coerce), in context.parameters. Default: none.

    describe_run ¶

    describe_run(
    action_name: str,
    values: Mapping[str, Any],
    view: DatasetView,
) -> tuple[str, str]

    Two short texts for the plot dock's source lines: what part of the view the run used (line 1, after the folder and revision, e.g. "shots 51–60 (10 of 60)"; "" for all of it) and its settings in short form (line 2, e.g. "last 10 shots · auto-crop 99 %"). The dock's tooltip always holds the full record. By default: no selection, and every parameter in use as title value (the Constants group left out: the dock adds the constants the run resolved).

    describe_result ¶

    describe_result(
    action_name: str, result: AnalysisResult
) -> str

    What a completed run found that the dock's settings line should add after describe_run's settings, in short form (e.g. a spectrum's resolution and Nyquist frequency, or a bin width chosen from the data); "" for nothing. Called for completed results only (as result_record). Default: nothing.

    parameter_warnings ¶

    parameter_warnings(
    action_name: str, values: Mapping[str, Any]
) -> List[str]

    Settings the run could not follow as given, and what it did instead (e.g. "X: min > max, using full extent"), for the dock's source line, its record and the settings tab.

    live_policy ¶

    live_policy(action_name: str) -> LivePolicy

    When a plot following Live reruns by default (the plot's settings can change it): on every new shot unless a long analysis declares fewer reruns.

    constant_keys ¶

    constant_keys(action_name: str) -> tuple[str, ...]

    The physical constants the analysis uses (physics.TABLE keys): its plots resolve them when each run starts, name them in their settings and source line, and are marked when a lab or folder value of one changes. Default: the keys of its Constants group (constant_layers.constants_specs); none without one.

    run_constant_keys ¶

    run_constant_keys(
    action_name: str, values: Mapping[str, Any]
) -> tuple[str, ...]

    Of constant_keys, the ones a run with these parameter values uses (e.g. the trap's only while a fit that needs them is on): its result records and names these, and only a change of one marks its plot. Default: all of constant_keys.

    run_constants ¶

    run_constants(
    action_name: str,
    values: Mapping[str, Any],
    layers: Mapping[str, Mapping[str, float]],
) -> ResolvedConstants | None

    The constants a run with these parameter values uses, from the lab and folder layers (AnalysisContext.constants) and the plot's own values. Pure (it runs on the GUI thread when the run is submitted). Default: the Constants group's choices (constant_layers.resolve_for_run); an analysis with its own override parameters returns its own resolution here, or None when this run uses no constants (it is then neither keyed on them nor marked when one changes).

    result_found ¶

    result_found(action_name: str, data: Any) -> dict[str, Any]

    What a completed run found or used beyond its parameters, as JSON values (fit results, the constants and where each came from), from compute's data, in the worker thread: kept as the result's found, in its record even after the plot is released. Its "reuse" entry, when given, is what the run decided beyond its parameters and input that a reuse must match too (e.g. a range kept from an earlier run of the plot): it goes into AnalysisResult.reuse_key. Default: nothing.

    minimum_size ¶

    minimum_size(action_name: str) -> tuple[int, int]

    The least size (width, height; logical pixels) of the action's plot in its dock, with its source lines, whatever it shows (the plot, its picture, an empty or failed run). Set by the script's design, not by the user. Default: PLOT_MINIMUM_SIZE.

    compute abstractmethod ¶

    compute(action_name: str, context: AnalysisContext) -> Any

    The numerical result (no Qt). Check context.cancelled() in long loops.

    Runs on the analysis worker thread. It reads the data only from context.view and never changes its arrays (copy one first).

    Parameters:

    • action_name (str) –

      The action the user ran (one of get_actions).

    • context (AnalysisContext) –

      The view, the effective parameter values and the run's constants.

    Returns:

    • Any –

      Anything render can draw; HeLab keeps it as the result's data.

    cache_supported ¶

    Whether the action's completed one-off runs may be saved in the disk cache and reused: for costly runs (a bootstrap, pair counting), not for quick ones. Default: no.

    cache_types ¶

    The dataclasses and enums compute's data may hold, and Reducers for objects saved by their data (a fit model: result_types.FIT_MODEL), for the default cache_pack and cache_unpack (helab.analysis.result_codec): only these are rebuilt from a file. Default: none (plain values, tuples, dicts and NumPy arrays only).

    cache_holds_state ¶

    cache_holds_state(action_name: str, owner: str) -> bool

    Whether the script keeps something for the plot owner between runs that a next run may start from (a box or a detection kept, pairs counted): its run may then differ from a plot's first run, so it is neither looked up in nor, unless cache_result says it is the same, saved to the disk cache. Default: nothing kept.

    Whether a completed one-off run gave what a plot keeping nothing would give (nothing kept from an earlier run used, every shot counted), so it may be saved (worker thread). Default: yes.
